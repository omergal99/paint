What should happen next?

Paint works well today. Before adding big new features, finish the evidence that makes it safe, reliable, and ready to ship as a production PWA.

The simple plan: make drawing and cleanup measurable, protect users’ work and memory, prove the release in real conditions, then build optional background removal, tabs, and Phase 3.

Already working

  • Ribbon, menus, settings, resize, transparency, colors, text safety, and pan.
  • Offline preparation and offline reload work locally.
  • Tests, documentation checks, and release checks pass.

Not finished yet

  • Proof that runtime events and pointer work clean up correctly.
  • Safe recovery from storage, quota, and large-image problems.
  • Production HTTPS/install proof, real-device checks, and Performance 90+.

After Phase 2

Phase 3: language, RTL, and a small notepad

First create a single message catalog; then language/RTL support; then a local, bounded plain-text notepad with tabs. No rich text, sync, or collaboration in the first version.

Three rules that prevent expensive mistakes

Keep the simple architecture

Stay with native ES modules unless measurement proves a bundler helps. The current browser journey has 49 local JS modules and no Fetch/XHR calls.

Do not weaken safety limits

The 64 MiB in-memory history cap is separate from browser storage quota. A bigger quota estimate is not permission to use more memory.

Do not promise unsafe text editing

Full edit-after-blur stays off until overlap, undo/redo, and reload tests prove pixels and text cannot be lost or duplicated.

Phase 2 is ready to call production-PWA ready when

  • Runtime pointer and teardown evidence is complete.
  • Storage, quota, recovery, and large-image failure paths are proven.
  • Missing test fixtures and type/coverage checks are complete.
  • Performance is near 90+ and a real HTTPS/device install-update matrix passes.
